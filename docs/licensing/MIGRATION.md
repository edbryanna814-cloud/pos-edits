# Migration and Rollout

**From:** in-app `PHM1` acceptance with issuance scripts in this repo
**To:** panel-issued `PHM2` entitlements, app verifies only
**Baseline:** `3f70318`

The migration must not strand a working pharmacy, must not lose data, and must
not leave a window where the old key can still mint licences.

---

## 1. Principles

1. **Contain first, migrate second.** Remove issuance capability before adding
   new verification.
2. **Installed devices keep working.** If any `PHM1` licence was sold, it stays
   valid until its own `exp`; no forced re-activation on upgrade day. Under the
   default ruling (`D-LIC-17`, no sales) there are none and no legacy path is
   built.
3. **No data migration by the customer.** The app never asks the pharmacy to
   move a database or a licence file by hand.
4. **One release can read both formats, only if needed.** If `D-LIC-17` is
   reversed, the first `PHM2` release accepts a stored `PHM1` code for
   verification but offers no way to enter a new one.
5. **The old key is retired, not trusted.** See §2.

---

## 2. Key containment and rotation (do this first)

The current key was generated by `scripts/license-keygen.mjs` into
`~/.pharmacy-pos-license/private.pem` and used by
`scripts/license-generator.mjs`. That is a developer-workstation key, and the
tooling is in the repo. Treat it as **exposed**.

| Step | Action | Evidence |
|---|---|---|
| K1 | Search every machine that ever built or issued a licence for `~/.pharmacy-pos-license/private.pem` and for copies of it | Search log, machine list |
| K2 | Record where it was found; do not delete yet | Inventory |
| K3 | Generate a new Ed25519 key pair in the panel environment; private key to KMS/secret store | Key id + creation record |
| K4 | Add the new public key to the app key set. Keep the old public key only if `D-LIC-17` is reversed and a legacy path exists; otherwise remove it after B3 | PR diff |
| K5 | Stop using `PHM1` for any new sale; issue only `PHM2` | Panel audit |
| K6 | Destroy the old private key once the new key is live and the rotation record is written. If `D-LIC-17` is reversed, destroy it after the last `PHM1` expires, or archive it offline under owner control | Destruction record |
| K7 | Remove `scripts/license-keygen.mjs` and `scripts/license-generator.mjs` from this repo and from build machines | Commit + CI scan |
| K8 | Add CI checks: no `BEGIN PRIVATE KEY`, no `generateKeyPair`, no signing call in app paths | CI config |

If K1 finds the key only on one developer machine and no licences were sold
yet, rotation is cheap and mandatory anyway. If licences were sold, note the
`lid`s issued with the old key for the panel import in §4.

## 3. Compatibility matrix (only if `D-LIC-17` is reversed)

Under the default ruling — no `PHM1` sales — this matrix is **not applicable**.
A device with no entitlement shows its device code, the owner registers it, and
the app claims a `PHM2`. Do not build a legacy reader for a licence that was
never sold. If the ruling is reversed, the matrix below applies.

| Installed state | First `PHM2` release behaviour | Next step |
|---|---|---|
| `PHM1`, valid | App verifies from the existing `license.json`; full function | At next renewal, panel issues `PHM2` |
| `PHM1`, expired | Read-only; no code entry | Panel issues `PHM2`; app claims |
| No licence / missing | Read-only or a status screen showing the device code | Panel registration |
| `PHM1` tampered/invalid | Read-only; support bundle | Panel registration after identity check |
| Dev build (`!app.isPackaged`) | Explicit development mode, visibly marked | Never sold |

The app must never delete a `PHM1` file it cannot verify. Keep it for support
diagnosis.

## 4. Importing existing customers into the panel

For every sold `PHM1` licence, create a panel record:

1. customer record (name, contact);
2. licence with `lid` matching the old payload `lid`, plan, price, currency,
   period, and `expires_at` = `floor(old exp_ms / 1000)` **seconds**;
3. a device row with `device_hash` equal to the old 32-hex `dev` value, status
   `active`;
4. an audit note: "migrated from PHM1, old key id, migrated by, date".

The old `dev` value is already the 32-hex lowercase hash of board/BIOS, and the
new design keeps that algorithm unchanged, so the value imports **directly**.
Do not add a salt, do not re-hash for lookup, and do not expect a 64-hex value.
If the panel wants a peppered form for logs, store it in the separate
`device_hash_hmac` column and never use it for lookup.

The default ruling `D-LIC-17` is that **no `PHM1` licences were sold**. In that
case this section is skipped entirely, legacy compatibility is not built, and
M3/M5/M7 are marked not applicable. Reverse that ruling only with written owner
confirmation.

## 5. Release sequence

```text
C0  Containment in the app repo: remove scripts, add CI + Vitest, correct docs
R0  Docs accepted (this package)
R1  Panel skeleton + key management + audit (no customer data)
R2  Panel: customers, licences, reverse enrolment, check-in, seats, revocation
R3  App: PHM2 verifier + cache + central write gate; remove code entry and
    license:apply; login stays allowed
R4  App: read-only mode, clock protection, support bundle, bilingual strings
R5  Migration: only if D-LIC-17 is reversed; otherwise not applicable
R6  Legacy retirement: only if R5 ran
```

C0 happens first, before R1. R1 and R2 can be tested with a staging deployment
and a test licence. R3 must not ship until the panel can issue a real
entitlement; otherwise the app has no way to regain access after read-only.

---

## 6. Rollout gates

| Gate | Condition | Stop if |
|---|---|---|
| M1 — Containment | Scripts removed, key rotation recorded, CI scan active | Any signing material remains in the repo |
| M2 — Panel ready | Can issue, renew, suspend, revoke, and enforce seats under concurrency | Seat overrun in the test |
| M3 — App compatible | Only if `D-LIC-17` is reversed: existing `PHM1` installation keeps working through upgrade | An installed till loses access |
| M4 — Read-only safe | Expiry and revocation leave data readable and exportable | Any data loss or hidden data |
| M5 — Migration | Only if `D-LIC-17` is reversed: every sold licence exists in the panel with a device row | A sold device cannot check in |
| M6 — Clean install | New device enrols from a fresh installer with no code entry | Any manual licence typing required |
| M7 — Legacy retirement | Only if `D-LIC-17` is reversed: no live `PHM1` entitlement remains | A legacy device would be stranded |

---

## 7. Rollback

- App rollback: the previous installer remains available; the local database is
  untouched by licensing changes. If `D-LIC-17` is reversed, a rollback
  re-enables `PHM1` verification because the previous build supports it;
  otherwise there is no live `PHM1` licence to honour.
- Panel rollback: restore the last database backup; signing keys are separate
  and must not be regenerated as part of a restore.
- If the panel is down during rollout, devices continue on cached entitlements
  for `POL-GRACE`; do not extend grace silently.

Rollback must never require a customer to re-enter a code. If it does, the
design has regressed.

---

## 8. Communication to existing customers

One short note, bilingual:

> The application now receives its licence automatically from the supplier.
> There is nothing to type or paste. If the app shows "read-only", contact the
> supplier with the device code shown on the status screen. Your data is safe
> and can always be exported.

No mention of fraud, piracy, or suspicion. No tax-compliance claim.

---

## 9. Post-migration checks

1. If `D-LIC-17` is reversed: every sold licence exists in the panel with the
   correct expiry; otherwise this item is not applicable.
2. Every registered device has checked in at least once.
3. No device is over its licence seat count.
4. The old key is destroyed or archived, not in use.
5. The app repo has no issuance code and no private key.
6. A fresh install can enrol with no typed code.
7. An expired device can export a backup.
8. The audit trail covers the migration itself.
